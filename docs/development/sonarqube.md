# SonarQube development setup

FlintFire uses the SonarQube server at <https://sonar.casadega.dev>. The project key is `flintfire`.
Keep `sonar-project.properties` and `.sonarlint/connectedMode.json` in lockstep if that key ever
changes.

## Layers

- **Local ESLint:** every active server rule implemented by the installed `eslint-plugin-sonarjs` is
  a blocking error on production `src/` (tests, scripts, and the website stay out of ESLint, as
  before).
- **Agent post-edit hook:** a type-independent subset of that profile, generated by RuleSync.
  Findings fail the hook.
- **Pre-push precheck:** the real Scanner over files changed vs `origin/main`. Exit 2 (Scanner,
  credentials, or server unavailable) is a loud skip; findings and analysis failures still block.
- **CI:** the Tests workflow uploads both Jest LCOV reports, then runs an inlined Sonar scan and the
  official quality-gate action. The server gate is **new-code-only** because this is a mature
  library, not a greenfield starter. Combined LCOV in Sonar is informational; path-specific gates in
  `scripts/check-coverage-gates.mjs` remain the coverage authority.

Neither the local plugin nor SonarQube for IDE replaces the server's complete analysis.

## CI setup

Create the project on the SonarQube server and configure these GitHub Actions values at the
**repository** level (avoid inheriting a different organization default):

| Name             | Kind     | Value                              |
| ---------------- | -------- | ---------------------------------- |
| `SONAR_TOKEN`    | Secret   | Project token with analysis access |
| `SONAR_HOST_URL` | Variable | `https://sonar.casadega.dev`       |

Attach a quality gate whose conditions are on **new code**, not “any open issue.”

The Tests workflow:

- runs on pull requests to `main` and on pushes to `main` (the latter establishes the new-code
  baseline);
- skips the Sonar job for pull requests from forks (GitHub does not expose repository secrets to
  those runs);
- checks out complete history at the PR head SHA (not the merge commit);
- restores `coverage/unit/lcov.info` and `coverage/integration/lcov.info`;
- supplies explicit PR or branch parameters for the Community branch plugin;
- waits for Compute Engine processing via the official quality-gate action.

The full CI scan is authoritative. Fork PRs still run lint, types, and both coverage gates.

## Manual re-scan

The `SonarQube Re-scan` workflow can analyze an already tested commit without rerunning the entire
quality pipeline. Open a completed `Tests` run, copy the numeric run ID from its Actions URL, and
supply it to the manual workflow. It restores that run's coverage artifacts and derives the original
PR or branch context before scanning.

## Local command-line setup

Install both SonarQube Scanner and SonarQube CLI. On macOS, Scanner is available through Homebrew:

```bash
brew install sonar-scanner
```

Install SonarQube CLI with SonarSource's installer, then authenticate once to the configured server:

```bash
curl -o- https://raw.githubusercontent.com/SonarSource/sonarqube-cli/refs/heads/master/user-scripts/install.sh | bash
sonar auth login --server https://sonar.casadega.dev
```

The CLI stores its user token in the macOS keychain. `sonar:precheck` reads that entry when
`SONAR_TOKEN` is not present, which also works when a GUI Git client does not inherit shell
environment variables. Other platforms can export a SonarQube user token as `SONAR_TOKEN`.

For profile synchronization, the committed `sonar.host.url` takes precedence over an inherited
`SONAR_HOST_URL`. Web API calls go through the authenticated SonarQube CLI, and synchronization
fails if the CLI's active server does not match the repository.

```bash
npm run sonar:rules
npm run sonar:precheck
npm run sonar:precheck -- --all
npm run sonar:precheck -- another-base-branch
```

`sonar:rules` intersects active server rule IDs with rules implemented by the installed
`eslint-plugin-sonarjs`. Before the project is provisioned it uses the server-default profiles;
afterward it automatically uses profiles associated with the project. `--bootstrap` remains the
offline fallback from the plugin's recommended configuration.

The normal precheck reports issues introduced compared with `origin/main`. `--all` includes
pre-existing issues in every changed file. The script uses a short-lived server branch and removes
it after reading the findings.

Never put Sonar tokens in source files, committed environment files, command arguments, or logs.

## Git hook behavior

Husky installs three complementary hooks during `npm install`:

- `pre-commit` runs the SonarQube CLI secret scan, then lint-staged.
- `commit-msg` enforces Conventional Commits through commitlint.
- `pre-push` runs the outgoing secret scan, the changed-file SonarQube analysis, then the existing
  unit coverage gate (`rules:check`, types, doc links, zod-idiom scan, unit coverage).

Secret scan failures always block. The changed-file server analysis exits with status 2 when
Scanner, credentials, the base branch, or the server is unavailable; pre-push reports the skip and
continues to the other checks. Findings, rejected credentials, and scanner failures still block.

## Coding-agent feedback

RuleSync generates a post-edit hook for Codex, Cursor, and Claude. The hook extracts edited
repository paths from each tool's event payload and runs a bounded, type-independent subset of the
generated SonarJS configuration, only on production `src/` files that `npm run lint` also analyzes.
Findings are printed near the edit and the hook exits unsuccessfully.

Edit `.rulesync/hooks.jsonc` or `scripts/agent-hooks/scan-edited-file.mjs`, then run
`npm run rules:sync`; do not edit generated tool hook files (`.cursor/hooks.json`,
`.claude/settings.json`, `.codex/hooks.json`) directly.

## SonarQube for IDE

The repository recommends the SonarQube for IDE extension and checks in the project binding. In VS
Code or Cursor, create a SonarQube connection whose ID is `https-sonar-casadega-dev`, point it at
<https://sonar.casadega.dev>, and bind using the `flintfire` key.
